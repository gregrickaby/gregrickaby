## Why getGamepads() is empty until you press a button

A website that could list every controller plugged into your computer, the moment you arrived, would learn a lot about you without asking. That's fingerprinting, and the [Gamepad spec](https://w3c.github.io/gamepad/) shuts it down: `navigator.getGamepads()` returns nothing until you press a button or move a stick while the page is open.

So any page that wants a controller has to ask for a button press first.

## Poll the controller with requestAnimationFrame

Most of the web works like a doorbell. You click, and the page gets a `click` event. You press a key, and it gets a `keydown`.

Controllers don't ring. There's an event when one connects and another when it disconnects, and that's it. **There is no event for pressing a button.** Instead, you take a picture of the whole controller, every frame, like a camera in burst mode:

```js
function poll() {
  // A snapshot of every controller, right now
  const pad = navigator.getGamepads().find((p) => p?.connected)

  if (pad) {
    console.log(pad.buttons[0].pressed) // the bottom face button
    console.log(pad.axes[0]) // the left stick, left (-1) to right (1)
  }

  // Do it again on the next frame, about 60 times a second
  requestAnimationFrame(poll)
}

requestAnimationFrame(poll)
```

That `?.connected` is there because Chrome always hands back four slots, and the empty ones are `null`. Plug in one controller, get one controller and three holes.

Each button gives you two things: `pressed`, a yes or no, and `value`, from `0` to `1`. On the face buttons, `value` is only ever `0` or `1`. Pull a trigger slowly in the box up top, though, and watch its `value` climb through every number in between. The trigger knows how far you pulled it.

> [!NOTE] Why not save the controller and reuse it?
> In Chrome, each `Gamepad` object is a snapshot, frozen the moment you got it. Hold on to last frame's and it never changes, so the buttons look stuck. That's why `poll` calls `getGamepads()` every time.

## Make the controller rumble with vibrationActuator

Scroll back up to that first box and find the two Rumble sliders. Push Strong up, leave Weak at 0, and press Rumble. Then swap them.

Your controller has two motors with off-center weights. On an Xbox controller, the big one in the left grip spins slow and heavy: that's `strongMagnitude`. The small one in the right grip buzzes: that's `weakMagnitude`. Here's all it takes:

```js
pad.vibrationActuator.playEffect('dual-rumble', {
  duration: 400, // milliseconds
  strongMagnitude: 0.6, // the big, slow motor
  weakMagnitude: 0.3, // the small, buzzy one
})
```

`playEffect` returns a promise that resolves with `"complete"` when the rumble finishes, or `"preempted"` if another one cut in first.

One catch before you build a game around it:

> [!WARNING] Not every browser can rumble
> Chrome (since version 68) and Safari (since 16.4) support `vibrationActuator`. Firefox doesn't, according to [MDN's compatibility data](https://developer.mozilla.org/en-US/docs/Web/API/GamepadHapticActuator/playEffect#browser_compatibility). Check that it exists before you call it, and treat rumble as a bonus, never the only way to tell a player something happened.

## The standard gamepad mapping: which button is A?

On an Xbox controller, the bottom face button says A. On a PlayStation controller, it's a cross. On a Switch Pro controller, the button in that spot says B, and A is on the right.

The Gamepad API doesn't care what's printed on the button. When a browser recognizes a controller, it sets `mapping` to `"standard"` and lays out the buttons the same way every time:

| Index    | Standard layout                              | Xbox        |
| -------- | -------------------------------------------- | ----------- |
| 0 to 3   | Bottom, right, left, and top face buttons    | A, B, X, Y  |
| 4, 5     | Left and right bumpers                       | LB, RB      |
| 6, 7     | Left and right triggers (analog, `0` to `1`) | LT, RT      |
| 8, 9     | Select and Start                             | View, Menu  |
| 10, 11   | Left and right stick presses                 | LS, RS      |
| 12 to 15 | D-pad up, down, left, right                  | D-pad       |
| 16       | Home                                         | Xbox button |

Axes `0` and `1` are the left stick, and `2` and `3` are the right one. Up on a stick is _negative_, because screens count `y` from the top.

So label your buttons by position. "Press the bottom button to jump" works on every controller. "Press A to jump" is wrong for every Switch player.

When a browser _doesn't_ recognize a controller, `mapping` is an empty string, and the buttons come in whatever order the device sends them. If yours shows up in the first box with `mapping: ""`, that's why it has no button names.

> [!NOTE] What about the Steam Deck?
> The Deck's built-in controls show up as an Xbox 360 controller through Steam Input, so the standard layout applies. In desktop mode, though, Steam turns the controls into a mouse and keyboard, and the browser sees no controller at all. Add your browser to Steam as a non-Steam game and launch it from there.

## Detect button presses and releases

A game needs to know more than "is the button down right now?" Jumping happens on the _press_, the one frame where the button goes from up to down. With no events, you work that out yourself: keep last frame's picture and compare.

```ts
for (const [i, down] of after.entries()) {
  if (down && !before[i]) pressed.push(i) // up last frame, down now
  if (!down && before[i]) released.push(i) // down last frame, up now
}
```

Once you know when a button comes up, you get one of the oldest tricks in platformers: variable jump height. Every jump starts at the same speed. If you let go while the ghost is still rising, its speed gets cut down to a slow float, and it tops out early. A tap is a hop. A hold is a full jump.

Try a tap, then a hold. Then turn variable height off and feel how stiff it gets:

<div data-demo="jump"></div>

Without variable height, every jump is the same arc no matter what your thumb does. It works, but it feels like the game isn't listening.

There's one more trap in that demo, and it's one I didn't see coming. Reload the page, and _only_ use your controller. No clicks, no keys. Jump.

No sound.

Browsers won't play audio until a visitor clicks, taps, or presses a key on the page. The [HTML spec](https://html.spec.whatwg.org/multipage/interaction.html#activation-triggering-input-event) lists exactly which input counts, and **controller buttons aren't on the list.** Mash them all you want. The page stays quiet until you touch the mouse or keyboard once.

That's why the level at the bottom asks for one click if it's playing silent.

## Coyote time, jump buffering, and double jumps

Here's something you've felt in every good platformer without knowing it had a name.

You run off a ledge and press jump a split second too late. In real physics, you're falling, so no jump. In a good game, you jump anyway. That's **coyote time**, named after the cartoon coyote who runs off a cliff and hangs in the air until he looks down. The game keeps letting you jump for a moment after the ground is gone.

The opposite happens too. You're falling toward a platform and press jump a split second _before_ you land. Strict physics says no, you're in the air. A good game remembers the press and jumps the instant you touch down. That's **jump buffering**.

Both windows are tiny. The level below uses 100 milliseconds for each, about six frames. You'll never notice them when they're there. You'll absolutely notice when they're gone.

Then there's the help everyone _can_ see: the **double jump**. Press jump again in midair, and the ghost kicks off of nothing at all. Physics would like a word. In code, it's one counter. Landing fills it, a jump in the air spends it, and an empty counter means no more jumps. Trimmed from the level:

```ts
if (grounded) airJumps = 1

if (pressed && !grounded && airJumps > 0) {
  vy = -DOUBLE_JUMP_SPEED // negative is up, since y counts down the screen
  airJumps -= 1
}
```

Want a triple jump? Change that `1` to a `2`.

The level has a switch for all three, and they all start off. Play it once like that. Then turn on coyote time and jump buffering and play it again. Then turn on double jump and watch the pits stop mattering.

## Cheat codes

- Ask for a button press first. Until then, the browser shows you no controllers at all.
- Poll every frame. There are no button events, so `requestAnimationFrame` and `getGamepads()` are the whole engine.
- Label buttons by position. "Bottom button" is right on every controller; "A" isn't.
- Treat sound and rumble as extras. A controller can't unlock audio, and not every browser can rumble.
